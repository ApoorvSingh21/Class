===============================================================
29.1 C AND OPERATING SYSTEMS
===============================================================

C is particularly important for system-level programming
because it provides relatively low-level control over:

    • Memory
    • Addresses
    • Data representation
    • CPU-oriented operations
    • Files
    • Processes
    • Hardware interfaces

A simplified relationship is:

        C PROGRAM
             |
             ↓
        C COMPILER
             |
             ↓
        MACHINE CODE
             |
             ↓
        OPERATING SYSTEM
             |
             ↓
        HARDWARE


For ordinary application programming, the program generally
does not directly control hardware.

Instead:

    Application
         ↓
    OS interface
         ↓
    Kernel
         ↓
    Hardware


===============================================================
KERNEL
===============================================================

The kernel is the privileged core of an operating system.

It manages resources such as:

    • CPU
    • Memory
    • Processes
    • Devices
    • Filesystems
    • Networking


A user program normally runs in user space.

The kernel operates with greater privileges.

Simplified:

    +----------------------------------+
    |          USER SPACE              |
    |                                  |
    |       C Application              |
    +----------------------------------+
                 |
                 | system call
                 ↓
    +----------------------------------+
    |          KERNEL SPACE            |
    |                                  |
    |   Process / Memory / Files /     |
    |   Device / Network management    |
    +----------------------------------+
                 |
                 ↓
             HARDWARE


===============================================================
29.2 SYSTEM CALLS — CONCEPT
===============================================================

A system call is a mechanism through which a user-space program
requests a service from the operating system kernel.

Examples of operations that commonly involve system calls:

    • Open a file
    • Read data
    • Write data
    • Create a process
    • Allocate/manage certain OS resources
    • Communicate with devices


Conceptually:

    C program
       |
       | request
       ↓
    system call interface
       |
       ↓
    kernel
       |
       ↓
    hardware/resource
       |
       ↓
    result


===============================================================
LIBRARY FUNCTION VS SYSTEM CALL
===============================================================

This distinction is extremely important.

A C library function is provided by the C library.

A system call is an operating-system interface.

They are related, but they are NOT the same thing.


For example:

    printf()
        ↓
    C standard library functionality
        ↓
    may ultimately use OS mechanisms


Whereas POSIX:

    write()
        ↓
    OS/POSIX interface for writing to a file descriptor


The exact internal implementation is platform-dependent.


===============================================================
29.3 PROCESSES — CONCEPT
===============================================================

A process is a running instance of a program together with its
execution state and associated resources.

For example:

    program executable
          ↓
       executed
          ↓
       PROCESS


A process generally has:

    • Code
    • Data
    • Stack
    • Heap
    • Registers/execution state
    • OS-managed resources


Simplified process memory:

    +----------------------+
    | Code / Text           |
    +----------------------+
    | Read-only data       |
    +----------------------+
    | Global / Static data |
    +----------------------+
    | Heap                 |
    |        ↓             |
    |                      |
    |        ↑             |
    | Stack                |
    +----------------------+


This connects directly with Chapter 20,
"C Memory Model."


===============================================================
PROGRAM VS PROCESS
===============================================================

PROGRAM:

    Passive executable/code.

PROCESS:

    Active executing instance.


Example:

    calculator executable
          ↓
    start it
          ↓
    process


You can potentially have multiple processes executing the same
program.


===============================================================
PROCESS STATES — CONCEPT
===============================================================

A process may conceptually move through states such as:

    NEW
      ↓
    READY
      ↓
    RUNNING
      ↓
    WAITING/BLOCKED
      ↓
    READY
      ↓
    RUNNING
      ↓
    TERMINATED


The exact process-state model depends on the operating system,
but this conceptual model is fundamental to OS understanding.


===============================================================
29.4 THREADS — CONCEPT
===============================================================

A thread is an execution path within a process.

A process can contain:

    one thread
or
    multiple threads


Conceptually:

    PROCESS
       |
       +---- Thread 1
       |
       +---- Thread 2
       |
       +---- Thread 3


Threads within the same process generally share process
resources such as:

    • Address space
    • Global data
    • Heap


But each thread has its own execution-related state, including
its own stack.


---------------------------------------------------------------
PROCESS VS THREAD
---------------------------------------------------------------

PROCESS:

    • Independent execution unit
    • Has its own address space
    • Generally more expensive to create/switch

THREAD:

    • Execution unit inside a process
    • Shares process address space/resources
    • Generally lighter than a separate process


Simplified:

    Process
       |
       +-- shared code
       +-- shared global data
       +-- shared heap
       |
       +-- Thread A -> own stack
       +-- Thread B -> own stack
       +-- Thread C -> own stack


===============================================================
WHY THREADS ARE USEFUL
===============================================================

Threads can allow a program to perform multiple activities
concurrently.

For example:

    Thread 1 → network communication
    Thread 2 → computation
    Thread 3 → user interface


However, shared memory creates synchronization problems.


===============================================================
RACE CONDITION
===============================================================

Suppose two threads access the same variable:

    int counter = 0;


Thread A:

    counter++;


Thread B:

    counter++;


If both operations happen concurrently without appropriate
synchronization, the final result may not be what the programmer
expects.

This is a race-condition/data-race type problem.

System-level C therefore requires understanding:

    • Shared memory
    • Synchronization
    • Atomicity
    • Mutual exclusion
    • Thread safety


The source syllabus introduces these topics conceptually here;
more advanced concurrency appears later in the overall roadmap.


===============================================================
29.5 FILE DESCRIPTORS — CONCEPT
===============================================================

A file descriptor is a small integer used by many POSIX systems
to identify an open file or other I/O resource within a process.

Typical standard descriptors are:

    0 → standard input
    1 → standard output
    2 → standard error


So:

    stdin  → descriptor 0
    stdout → descriptor 1
    stderr → descriptor 2


Conceptually:

    Process
       |
       +---- FD 0 → stdin
       |
       +---- FD 1 → stdout
       |
       +---- FD 2 → stderr
       |
       +---- FD 3 → some opened file
       |
       +---- FD 4 → another resource


===============================================================
FILE POINTER VS FILE DESCRIPTOR
===============================================================

These are NOT the same concept.

C standard I/O commonly uses:

    FILE *

Example:

    FILE *fp;


POSIX low-level I/O commonly uses:

    int fd;


Example:

    int fd;


Relationship conceptually:

    FILE *
      ↓
    C stdio stream
      ↓
    may ultimately use
      ↓
    file descriptor / OS interface


Do not confuse:

    FILE *
with
    int file descriptor


===============================================================
29.6 MEMORY MANAGEMENT — CONCEPT
===============================================================

Memory management occurs at multiple levels.

C provides mechanisms such as:

    malloc()
    calloc()
    realloc()
    free()


The operating system manages the process's virtual memory and
maps it to physical memory as appropriate.


Simplified:

    C program
        |
        | malloc()
        ↓
    C runtime / allocator
        |
        ↓
    OS-managed virtual memory
        |
        ↓
    Physical memory


This is a conceptual model; the exact implementation depends on
the operating system and runtime.


===============================================================
VIRTUAL MEMORY — CONCEPT
===============================================================

Modern operating systems commonly provide each process with its
own virtual address space.

Conceptually:

    Process A
    virtual addresses
          |
          ↓
       OS/MMU
          |
          ↓
    physical memory


and:

    Process B
    virtual addresses
          |
          ↓
       OS/MMU
          |
          ↓
    physical memory


This provides isolation between processes.


---------------------------------------------------------------
IMPORTANT
---------------------------------------------------------------

A pointer value in a C program is an address within the
program's address space.

It should NOT be interpreted as a direct physical RAM address.


===============================================================
29.7 C AND HARDWARE
===============================================================

C is widely used close to hardware because it provides:

    • Pointers
    • Integer types
    • Bitwise operations
    • Structures
    • Low-level memory access
    • Predictable object representations in many practical
      environments
    • Efficient compiled code


This makes C important for:

    • Operating systems
    • Device drivers
    • Embedded systems
    • Firmware
    • Compilers
    • Networking software
    • Performance-critical software


===============================================================
MEMORY-MAPPED HARDWARE — CONCEPT
===============================================================

Some systems expose hardware registers through addresses.

Conceptually:

    hardware register
          ↑
          |
    memory address
          ↑
          |
       C pointer


A simplified example might look like:

    volatile unsigned int *reg =
        (volatile unsigned int *)ADDRESS;


Then:

    *reg = value;


However, actual hardware addresses, register definitions,
permissions, and required qualifiers depend on the target
platform.

Do NOT treat arbitrary addresses as valid portable C programs.


===============================================================
WHY volatile MATTERS
===============================================================

Hardware registers may change independently of ordinary program
flow.

For example:

    hardware
       |
       ↓
    register value changes
       |
       ↓
    C program reads register


The compiler must not incorrectly assume that the value can
never change for reasons outside ordinary C execution.

This is one important use case for:

    volatile


Example conceptually:

    volatile unsigned int status;


Important:

    volatile does NOT automatically make an operation atomic.

It also does not provide general thread synchronization.

    +------------------------+

    +------------------------+

Embedded programming often emphasizes:

===============================================================
29.9 POSIX OVERVIEW
===============================================================

POSIX is a family of standards specifying interfaces and
behavior for operating-system environments.

It is especially associated with Unix-like systems.

The source syllabus introduces:

    open()
    read()
    write()
    close()
    fork()


These are important concepts for system-level C programming.


===============================================================
open()
===============================================================

Conceptually:

    open()
       ↓
    requests an OS resource/file to be opened
       ↓
    returns a file descriptor


Simplified usage:

    int fd = open("data.txt", ...);


On success:

    fd >= 0


On failure:

    fd == -1


The exact arguments depend on the desired flags and platform
interface.


===============================================================
read()
===============================================================

read() conceptually reads bytes from a file descriptor.

Example form:

    ssize_t n = read(fd, buffer, size);


Conceptually:

    file/device
        ↓
      read()
        ↓
      buffer


The return value represents how many bytes were read, with
negative return indicating an error in the usual POSIX model.


===============================================================
write()
===============================================================

write() sends bytes to a file descriptor.

Conceptually:

    ssize_t n = write(fd, buffer, size);


Flow:

    buffer
       ↓
     write()
       ↓
    file/device/output


Again, the return value indicates the number of bytes written
or an error according to the POSIX interface.


===============================================================
close()
===============================================================

close() releases a file descriptor.

Example:

    close(fd);


Typical lifecycle:

    open()
      ↓
    read()/write()
      ↓
    close()


Forgetting to release resources can cause resource leaks.


===============================================================
open / read / write / close
===============================================================

The classic low-level I/O pattern is:

    fd = open(...)
          |
          ↓
    read()/write()
          |
          ↓
       close()


Compare with C standard I/O:

    FILE *fp = fopen(...)
          |
          ↓
    fread()/fwrite()/fprintf()
          |
          ↓
    fclose()


These are two different abstraction levels.


===============================================================
fopen() VS open()
===============================================================

fopen():

    • C standard library
    • Returns FILE *
    • Stream-oriented
    • Used with fprintf(), fgets(), fread(), etc.


open():

    • POSIX/OS interface
    • Returns file descriptor
    • Low-level file-descriptor-oriented I/O


Similarly:

    fclose()
        ↔
    close()


and:

    fread()/fwrite()
        ↔
    read()/write()


They are related but not interchangeable concepts.


===============================================================
fork() — CONCEPTUAL INTRODUCTION
===============================================================

fork() is a POSIX process-creation mechanism.

Conceptually:

    Parent Process
          |
        fork()
          |
      +---+---+
      |       |
      ↓       ↓
   Parent   Child


After a successful fork(), there are two processes.

This is one of the most important concepts in Unix-like
process management.


---------------------------------------------------------------
CONCEPTUAL RETURN VALUES
---------------------------------------------------------------

In the parent:

    fork() returns child's process ID.

In the child:

    fork() returns 0.

On failure:

    fork() returns -1 in the calling process.


Example conceptual pattern:

    pid_t pid = fork();

    if (pid < 0)
    {
        /* error */
    }
    else if (pid == 0)
    {
        /* child */
    }
    else
    {
        /* parent */
    }


The exact process behavior and resource semantics are governed
by the POSIX/operating-system environment.


===============================================================
FORK MEMORY CONCEPT
===============================================================

Before fork:

    Parent
       |
       +---- code
       +---- data
       +---- heap
       +---- stack


After fork conceptually:

    Parent                 Child
       |                      |
       +---- code             +---- code
       +---- data             +---- data
       +---- heap             +---- heap
       +---- stack            +---- stack


Modern operating systems commonly optimize this using
copy-on-write techniques.

Conceptually:

    Initially:
        pages can be shared

    On modification:
        required pages are copied

===============================================================
IMPORTANT INTERVIEW COMPARISONS
===============================================================

1. PROGRAM vs PROCESS

Program:
    Passive code/executable.

Process:
    Running instance with execution state/resources.


---------------------------------------------------------------

2. PROCESS vs THREAD

Process:
    Separate address space.

Thread:
    Execution unit sharing process resources.


---------------------------------------------------------------

3. FILE* vs FILE DESCRIPTOR

FILE*:
    C standard I/O stream.

File descriptor:
    Integer identifier used by POSIX-style low-level I/O.


---------------------------------------------------------------

4. fopen() vs open()

fopen():
    Standard C library.

open():
    POSIX interface.


---------------------------------------------------------------

5. fread() vs read()

fread():
    C standard library stream operation.

read():
    POSIX file-descriptor operation.


---------------------------------------------------------------

6. fclose() vs close()

fclose():
    Closes a C stream.

close():
    Closes a file descriptor.


---------------------------------------------------------------

7. malloc() vs OS MEMORY MANAGEMENT

malloc():
    C library allocation interface.

OS memory management:
    Kernel-level management of virtual/physical memory resources.


---------------------------------------------------------------

8. volatile vs atomic

volatile:
    Communicates that an object may have externally observable
    changes requiring accesses to be performed as specified by
    the language rules.

atomic:
    Provides atomic operations and synchronization semantics.

Therefore:

    volatile != atomic


===============================================================
COMMON SYSTEM-LEVEL C MISTAKES
===============================================================

MISTAKE 1:

Thinking C pointers are physical RAM addresses.

WRONG.

A pointer is an address within the relevant program/address
space model.


---------------------------------------------------------------

MISTAKE 2:

Thinking FILE* and file descriptor are identical.

WRONG.

They belong to different abstraction layers.


---------------------------------------------------------------

MISTAKE 3:

Thinking volatile solves thread races.

WRONG.

volatile is not a general synchronization mechanism.


---------------------------------------------------------------

MISTAKE 4:

Thinking a process and a program are identical.

WRONG.

A program is code; a process is an executing instance with
associated state/resources.


---------------------------------------------------------------

MISTAKE 5:

Thinking threads have completely separate memory.

WRONG.

Threads in the same process generally share the process's
address space, while each thread has its own execution stack.


---------------------------------------------------------------

MISTAKE 6:

Thinking malloc() directly means "give me physical RAM."

WRONG.

Memory allocation occurs through layers including the C runtime
and operating-system memory mechanisms.


===============================================================
GATE / INTERVIEW QUESTIONS
===============================================================

Q1. What is a system call?

A:

A mechanism through which a user-space program requests an
operating-system service.


Q2. What is a process?

A:

A running instance of a program together with its execution
state and associated resources.


Q3. What is a thread?

A:

An execution unit within a process.


Q4. Do threads in the same process generally share heap memory?

A:

Yes.


Q5. Do threads have independent stacks?

A:

Generally, each thread has its own stack.


Q6. What is a file descriptor?

A:

A small integer used by POSIX systems to identify an open file
or other I/O resource within a process.


Q7. What are the conventional standard file descriptors?

A:

    0 → stdin
    1 → stdout
    2 → stderr


Q8. What does open() return on success?

A:

A file descriptor.


Q9. What does fork() create?

A:

A new process, producing parent and child execution contexts.


Q10. What is the difference between FILE* and int fd?

A:

FILE* represents a C standard I/O stream.

fd represents a POSIX-style file descriptor.


Q11. Does volatile guarantee atomicity?

A:

No.


Q12. Why is C widely used for embedded systems?

A:

Because it provides efficient compiled code, pointers, bitwise
operations, direct interaction with memory-oriented interfaces,
and relatively low runtime overhead.
